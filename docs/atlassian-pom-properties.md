# Atlassian Maven build descriptors (`pom.properties`)

Answers the version-fingerprint read that a limited-file-read primitive
against Jira / Confluence is pointed at first, including the
`/s/<token>/_/;/…` servlet-read prefix the sweep delivers it behind.

## Paths

| Path | Answers |
| --- | --- |
| `/META-INF/maven/com.atlassian.jira/jira-webapp-dist/pom.properties` | `atlassian-pom-jira` |
| `/META-INF/maven/com.atlassian.confluence/confluence-webapp/pom.properties` | `atlassian-pom-confluence` |
| the same two under `/jira`, `/confluence`, `/atlassian-jira` context paths | as above |
| `/s/<token>[/<seg>…]/_/[;<seg>/]<any path above>` | as above, `trapWalkDepth` > 0 |

Method: `GET`. Response: `200 text/plain`, five lines. No canary is
requested and none is issued — the body is a build number, not a secret,
so the trap costs no upstream quota and runs on a keyless deployment.

## What it serves

Maven's generated artifact descriptor, in the shape the plugin writes it:
a `#Generated by Maven` marker, a timestamp comment, then `version`,
`groupId`, `artifactId`. The version comes from `HONEYPOT_JIRA_VERSION`
(default `8.13.4`) and `HONEYPOT_CONFLUENCE_VERSION`, and is pinned inside
the affected range for the read issue that reaches this descriptor — a
patched build number ends the exchange before the escalation the trap
exists to observe. The timestamp is generated per response: it is not a
secret, but a byte-identical descriptor on every host that serves one is a
fleet fingerprint, and a plausible build date costs nothing to vary.

## The servlet-read prefix

Jira and Confluence serve static webapp resources under a cache-busting
`/s/<token>/_/<resource>` prefix. The file-read issues in that family aim
at the static resolver and insert a `;` segment ahead of the resource, so
the container's security constraint — which matches on the literal servlet
path — does not cover it while the resolver still returns the file.

That prefix is transport, not part of the filename, so
`_atlassian_servlet_read_trap` strips it and re-resolves the remainder
rather than enumerating it onto every trap a read primitive might reach.
It is bounded to the exact trap table with no layout walk: only a file that
would already be answered when asked for directly becomes reachable
through the prefix. A genuine static-resource request under the same
prefix (plugin CSS, for example) still gets a 404 — answering that with a
build descriptor would be a louder tell than the 404 it replaces.

Switch: `HONEYPOT_ATLASSIAN_SERVLET_READ_ENABLED` (default on). Turning it
off leaves the direct paths resolving, since those are the layout walk's
business.

## Why

Scanner populations that walk a broad multi-product exploit dictionary
probe this descriptor as reconnaissance: every subsequent exploit choice
for these products depends on the build number, so the read is the step
that decides whether the sweep escalates at all. A 404 ends the exchange
with nothing recorded but a path.

The populations observed spelling this path are the same ones that
enumerate deeper whenever a surface answers them, so the measurement the
trap is built for is exploit-chain progression: which version-specific
request this population reaches for once it believes it has a vulnerable
target. That is a behaviour a 404 cannot produce, and it is not otherwise
visible — the credential-bearing Atlassian files a chain like this ends at
are already covered elsewhere in the table, but nothing was answering the
question that gates the chain.
